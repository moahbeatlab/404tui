carries a few real samples (a 2.5 s tone on B5) and a real pattern (B2, `kick` / `snare` / `hat`), so
the Slicer and the Sequencer show their working state and not an empty one.

## The samples in the shots

The sim's own material is generated tones, a constant-amplitude sine, so its waveform has no peaks
and says little about what the Slicer does. The Slicer shots therefore use a **real recording**, whose
hits show in the waveform and line up with the slice boundaries.

A simulated unit can be built from a real folder — `sp404 -offline <dir>` runs `sim.OpenFolder` over
it — so the break is loaded from a folder, not from the sim's built-in tones:

    mkdir -p /tmp/404lib/PROJECT_01 /tmp/404lib/SD/IMPORT
    # a folder holding PADCONF.BIN is a project; a valid blank one can be made
    # with formats.NewPadconf(nil, "PROJECT_01").Bytes()
    cp drum_break.wav /tmp/404lib/SD/IMPORT/
    tmux -L shots new-session -d -s ui -x 140 -y 45 \
      "XDG_CONFIG_HOME=/tmp/404cfg /tmp/sp404 -offline /tmp/404lib"

`XDG_CONFIG_HOME` points the program at a throwaway config, for two reasons: the slicer keeps the
slices of every sample it has opened in `slices.json` (keyed by the file, and restored on opening),
so a second take would not start from the 8 default slices; and the capture should not write into
your own `~/.config/404tui`.

Then tab `2` (Files), `Tab` into the file column, and `Z` on the WAV — the Slicer opens on it. `t`
finds the onsets (32 on this break), which is the clearest proof the boundaries follow the audio.

The break used is Wikimedia Commons' **Drum beat.ogg** (CC), converted to 44.1 kHz 16-bit WAV. Only
WAV, AIFF, FLAC and MP3 are decoded, so an OGG has to be converted first:

    ffmpeg -i drum_beat.ogg -ar 44100 -ac 2 -c:a pcm_s16le drum_break.wav

## How they are taken

The program is driven in a **private tmux socket** — never the default one, which hosts other
sessions (see `docs/claude-memory/feedback_tmux_private_socket.md`). A plain `tmux kill-server` has
ended a work session before; `tmux -L shots kill-server` only touches the capture server.

    go build -o /tmp/sp404 ./cmd/sp404
    tmux -L shots new-session -d -s ui -x 140 -y 45 "/tmp/sp404 -sim"
    # then, per tab: send-keys the tab number, capture with -e for the ANSI colour
    tmux -L shots capture-pane -e -t ui -p > pads.ansi
    tmux -L shots kill-server

The Slicer and the Sequencer need keys, not just the tab number, and the view settles a few seconds
after each one — send the key, **wait, then capture**, or the shot lands on the previous state:

    # Slicer on a real file: -offline (above), tab 2, Tab, Z, then ~10 s
    # Sequencer on the sim's own pattern: tab 5, `a`, then Enter on slot 2 (B2)
    #   the pattern chooser loads asynchronously; give it ~8 s before the shot

`capture-pane -e` keeps the escape sequences, so the colour survives. [`render.py`](render.py) turns
that into the PNG, one cell per character, at 1456×944 for 140×45 cells:

    python3 docs/img/render.py pads.ansi docs/img/pads.png

It needs Pillow and two fonts: a monospaced one for the text (DejaVu Sans Mono) and one that has the
**Braille block** (FreeMono or DejaVu Sans). The Slicer draws its waveform, and the dot graphs on
other tabs, in Braille characters, and DejaVu Sans Mono has none: with it every dot cell becomes an
empty box, so the waveform looks like a solid wall of boxes whatever the audio is. The script uses a
second font for those characters and stops with a message when it cannot find one, instead of writing
a picture like that. If a shot ever shows rows of hollow boxes, that is the cause.

Nothing in this folder is generated by the build — the pictures are committed, so they need re-taking
only when a view changes.
